Native Framer implementation plan

Create six page layouts using native Stacks, type styles, image layers, links and reusable components. Define Films, Directors and News collections, with CMS references from films to directors, approval/source fields, and metadata fields. Client remains workspace owner. Avoid representing the present local browser editor as an included third-party CMS.

For sections, the straightforward native workflow is a client-editable vertical Stack with four approved components in Assets. The owner can insert/duplicate components, drag their order and toggle visibility. Bind text/images and approved visibility flags where supported. A content-editor-only CMS page-builder with arbitrary section ordering requires a separately validated Sections collection, conditional component variants and an ordered collection list, or a custom component. It is not promised as an out-of-box CMS permission feature.

Use the native video component or Vimeo embedding with autoplay/muted/loop, a poster, aspect-ratio control and pause behaviour. Use native opacity/transform transitions; respect reduced motion and keyboard focus. Test all bindings and permissions inside the real Framer project before calling the native build complete. The supplied local simulation proves the intended workflow; it does not prove an account-specific Framer implementation.

Days 1–3: validate content, rights, founding date, template and layout. Days 4–10: native Framer pages and CMS. Days 11–15: content import, final showreel, studio photos, sections and forms. Days 16–18: responsive, accessibility, SEO and redirect tests. Days 19–21: client acceptance, domain switch, rollback readiness and real Framer training video. Client content and account access must arrive on time for this schedule.

GoDaddy migration and email preservation

Preparation only. No client account has been accessed or altered. Export the DNS zone from GoDaddy and save a dated BIND file plus screenshots of records and TTLs. Identify the authoritative DNS provider and existing mail provider; registration at GoDaddy does not prove DNS or email is hosted there. See GoDaddy’s export procedure.

  1. Record current A/AAAA/CNAME values, nameservers and web aliases, plus every MX and TXT entry. Inventory SPF, DKIM selectors, DMARC, verification records, autodiscover and mail hostnames. Obtain DKIM selectors from the mail provider rather than guessing them.
  2. Before switching, confirm the live Framer site, approved content, HTTPS, redirects and target domains. Re-test the exact domain records shown in the project’s Domains panel against current Framer instructions. Keep nameservers at the existing provider unless a separately approved DNS migration is required.
  3. Change only the web-serving A/AAAA or www CNAME entries needed by Framer. Preserve MX, SPF, DKIM, DMARC, verification and mail service records. Resolve conflicting web records only after identifying their purpose. A new host does not require moving mail or transferring the registrar.
  4. Test the apex and www host, HTTP→HTTPS, certificate, canonical host, all six pages, original paths and representative 301s. Verify no redirect chains or loops. The 107-row redirect table is a preparation inventory, not an automatically imported Framer configuration: host/protocol rules belong at the hosting layer, and query-based WordPress aliases need explicit routing support or an approved edge rule if the platform cannot match queries.
  5. Test inbound and outbound mail with an authorised test mailbox and an external provider. Check message headers for SPF/DKIM/DMARC results, replies and normal mail clients. Compare MX/TXT values to the saved inventory. Do not send emails or change policies without the client’s approval.
  6. Observe during propagation and keep the previous host available. If the web switch fails, restore the saved web record values and TTLs, leaving mail records untouched. Re-test both hosts and mail. Never import a full DNS zone blindly: GoDaddy imports merge records and can conflict with existing entries. Confirm rollback with the client before closing the change window.

The 107 planned redirects cover the published pages exposed by the WordPress API, navigation and root sitemap, plus canonical/ID aliases. The public API returned no published posts. Access logs, historical backlinks and private routes were unavailable, so an absolute claim about all historic URLs would be unsupported. The 99-route proposed final sitemap excludes admin and demonstration URLs and is not installed on the client site.
